# 任务调度与可观测规划

面向：本地长期跑 job 不混乱、可排错、可恢复。

## 1. 单一编排入口

**需求**

- 系统级 cron/systemd 只调用一个编排入口（脚本或小型 CLI），由编排器按依赖顺序调用子 job。
- 避免多个 shell 散落各处且顺序不一致。

**验收建议**

- 新机器按文档只配置一条定时任务即可跑通「最小可用流水线」。

**技术备注**

- 与 `instock/job/execute_daily_job.py` 及 `instock/bin/run_job.sh` 演进对齐。

---

## 2. 任务依赖与阶段划分

**需求**

- 明确定义阶段：如「基础行情 → 元数据/列表 → 指标/形态 → 选股/回测预计算」。
- 下游任务在上游失败时可配置：跳过、重试 N 次后失败、或标记降级运行。

**验收建议**

- 人为使上游失败时，行为符合配置且日志清晰。

---

## 3. 重试与退避

**需求**

- 网络类子任务支持重试与指数退避，避免打爆数据源或被封。
- 记录每次重试原因与 HTTP 状态（若适用）。

**验收建议**

- 模拟 503 时重试次数与总耗时在预期上限内。

---

## 4. 幂等与 CLI 约定

**需求**

- 各子 job 统一支持：`--date`、`--from/--to`、`--force` 等（具体命名可统一规范文档）。
- `execute_daily_job` 中「默认启用哪些步骤」与「全量/开发裁剪」用配置或环境变量区分，避免靠注释代码区分环境。

**验收建议**

- README 与 `run_job.sh` 中的说明与真实 CLI 行为一致。

---

## 5. 可观测性

**需求**

- 每次编排运行生成：run_id、开始结束时间、每步状态、行数统计、异常栈摘要。
- 可选：复用或扩展 Web 端「同步/作业」API（`instock/web/sync_*`）展示最近 N 次运行。

**验收建议**

- 失败时能在 5 分钟内从日志或 DB 定位到失败步骤与首条错误信息。

---

## 6. 日志规范

**需求**

- 结构化或半结构化日志（至少统一前缀：run_id、job_name、trade_date）。
- 日志轮转（logrotate 或应用内按大小切割），避免撑满磁盘。

**验收建议**

- 长期运行一周后磁盘占用在预期上限内。

---

## 7. 配置分层

**需求**

- `dev` / `prod`（或 `local` / `server`）配置分离；路径与 DB 用环境变量。
- 提供 `.env.example` 列出全部变量。

**验收建议**

- 无 `.env` 时默认连接本地开发库且行为安全（不误连生产）。

---

## 8. 资源与并发

**需求**

- 文档说明：线程/进程池并发度与 MySQL 连接数、数据源限流的关系。
- 高峰任务可限流或分时（如收盘后两小时再跑重型任务）。

**验收建议**

- 并发参数调整后，无连接池耗尽或死锁（压力场景下验证）。
