# 数据覆盖与缺失日管理 — 实施计划

本文档落在仓库内，便于版本管理与评审；与对话无关，以本文件为准迭代。

**原则**：「缺哪些日」以 **数据库按表统计 + 交易日历差集** 为准；**哪次同步任务跑的** 以 **`sync_job_history` / 扩展账本** 为准；二者不对等（任务成功 ≠ 当日数据完整）。

---

## 阶段 0：约定与目录

| 事项 | 说明 |
|------|------|
| **交易日历来源** | 明确唯一来源：沿用现有交易日抓取结果对应的表，或单独维护 `trade_calendar`（若尚无则新增并定时同步）。 |
| **日期粒度** | 统一按 **交易日 `trade_date`（DATE）**；避免自然日与交易日混用。 |
| **「数据集」定义** | 每个数据集一个稳定 `dataset_id`（如 `spot`、`selection`、`fund_flow`），对应业务含义 + 查询表 + 日期列。 |

**产出**：与本文件同级可增补「数据源说明」小节；与 [`database-schema.md`](./database-schema.md) 交叉引用。

---

## 阶段 1：集中维护「数据集 → 表 → 日期字段」映射

| 事项 | 说明 |
|------|------|
| **配置形态** | 推荐仓库内独立配置：如 `instock/config/data_coverage_map.yaml` 或 `instock/core/data_coverage_registry.py`。 |
| **每条映射建议字段** | `dataset_id`、`title`、`mysql_table`、`date_column`、可选 `where_sql`、可选 `job_ids`（关联同步作业）。 |
| **首批范围** | 先覆盖 3～5 个最关心的数据集，其余按需追加。 |

**产出**：单一真相映射 + 在本文或 `jobs.md` 中注明「新增业务表时如何登记一行」。

---

## 阶段 2：SQL 化「应有日 − 已有日」差集

| 事项 | 说明 |
|------|------|
| **核心 SQL 模式** | 交易日历与 `SELECT DISTINCT date_column FROM biz_table WHERE …` 做差集，得到缺失日；附 `MIN/MAX/COUNT(DISTINCT)`。 |
| **实现位置** | 建议在 `instock/lib/` 新增模块（如 `data_coverage.py`）。 |
| **性能** | 对 `date_column` 建索引；大范围查询先缩小日历区间。 |
| **API（可选）** | `GET .../coverage/summary`、`.../coverage/gaps?dataset=&start=&end=`。 |

---

## 阶段 3：扩展任务账本与 sync 对齐

| 事项 | 说明 |
|------|------|
| **现状** | `instock/log/sync_job_history.json` 已有 job、日期参数、成败等，适合审计。 |
| **轻量扩展** | 任务成功结束时写摘要：`run_id`、`job_id`、日期参数、`finished_at`。 |
| **加重方案** | 新表或 JSONL：`run_id`、`dataset_id`、日期区间、状态，便于与阶段 2 并排展示。 |
| **与阶段 2 关系** | 页面：**缺失日**来自 DB 差集；**上次谁跑的**来自账本；勿混为一谈。 |

---

## 阶段 4：Web 展示（可选）

| 事项 | 说明 |
|------|------|
| **「数据覆盖」页/区块** | 按数据集展示日期范围、覆盖交易日数、缺失日列表；可链到某次 `run_id`。 |
| **数据同步页** | 保留触发与日志；可通过映射里的 `job_ids` 链到覆盖页。 |

---

## 阶段 5：运维纪律

| 表名或日期字段变更时，同步改 **映射配置**；可选：单测校验「映射中的表与列存在」。

---

## 建议实施顺序

1. 阶段 0 + 1（日历约定 + 映射文件 + 文档指针）  
2. 阶段 2（差集查询，可先脚本后 API）  
3. 阶段 4 最小版（summary + 简单表格）  
4. 阶段 3 按需（账本轻重选一）  
5. 阶段 5 随成熟度加强
